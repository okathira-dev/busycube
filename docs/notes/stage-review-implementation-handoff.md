# ステージ実装への引き継ぎ

更新: 2026-10-26。レビュー・事前PoCを終え、次のセッションから実装へ進むための入口。

## 現在地と読む順番

1. リポジトリのAGENTS.mdと、対象に応じた.cursor/rulesの正本を読む。
2. [対話で確認した方針](./stage-review-decisions.md)を実装変更の合意として読む。各項目の最新の明示的な結論を優先する。
3. [PoC結果](./stage-review-poc-results.md)で成立条件、実測範囲、未観測、実装に使えるコードを確認する。
4. [初回AIレビュー](./stage-review-puzzle-ai.md)は指摘の背景。採用されなかった提案を復活させない。
5. [人手確認台帳の入口](./stage-review.md)からD・P・Lの実施記録を確認する。既存の結果は維持する。

現コード・JSDocは現行動作の正本であり、合意済みの改修後仕様が反映されているとは限らない。コードと合意の差を実装する。合意文書同士が矛盾して最新の結論を判定できなければ、その項目だけを切り分けて確認する。

レビューの一巡と事前PoCは終了済み。以前成立を確認したAPIを再びPoCし、ユーザーの再確認を待つことを実装開始の条件にしない。S-400もPCで確認できた範囲で区切る合意済み。他端末のスリープ挙動を網羅する追加試験は求めない。未観測の挙動を実測済みに書き換えず、本実装中の確認事項として持つ。

一部の最終決定は「メモ（検討中）」にも残る。特にS-340・S-400は、その見出しだけを理由に未合意へ戻さない。「対応済み」のPoC記録もゲーム本体の実装完了とは区別する。

## 作業中の変更を引き継ぐ

- 引き継ぎ時のブランチはstage-review-and-improve。次のセッションでも最初に実際のbranch・status・diffを確認する。
- レビュー文書には既存のステージ済み変更と、その後の未ステージ変更が混在する。PoCには未追跡ファイルもある。この作業ではコミット・push・デプロイをしていない。
- 未コミット・未追跡のPoCと文書も成果物。reset、clean、checkout等で失わない。別checkoutへ移る場合は、必要な差分と未追跡ファイルを引き継げることを先に確認する。
- ゲーム本体の合意済み改修は原則これから。PoCを触ったことで製品ステージまで更新済みと判定しない。
- 検証に使ったPC用URLは[PoC一覧](http://127.0.0.1:5173/poc/)。localhost:5173では別アプリが見える競合を観測した。他アプリのサーバーを停止しない。新セッションでサーバーの生存は改めて確認する。
- AndroidはUSB転送で端末側localhostを使う。LAN IPのHTTPをsecure contextとみなさない。PCの127.0.0.1と端末のlocalhostの保存状態は共通ではない。

## 実装の進め方

1. 合意文書から、維持・改修・削除・統合・分離・追加・保留の作業表を作る。各行にstage ID、依存先、実装状態、検証状態を持たせる。状態は以後のセッションでも追える形で更新する。
2. 基本はD→P→L。D-001/S-000とD-002/S-010は現状維持なので、最初の実装はD-003/S-020。小さい作業単位で実装と検証を終え、順に進める。
3. 統合・分離等の依存関係は同じ作業単位にまとめるか、後続依存として明示する。統合先がまだないまま既存の解ける箱だけを先に削除しない。
4. ステージ内のコード・locale・style・解法JSDoc・必要なfixture・manifestを揃える。削除・追加・分類変更時は索引生成と参照先、進捗IDの扱いも確認する。
5. 各作業単位を検証後、実装済みと人手検証待ちを分けて記録する。「メモ」から「対応済み」への移動は実施した範囲と証跡に合わせる。実装しただけで既存の人手チェックを合格にしない。
6. 残りは実装・統合後の動作確認。通常の実装判断で進められるものは進め、確定したギミックを最初から再相談しない。設計変更が必要な技術上の不成立が見つかった場合だけ、影響範囲と代案を整理する。

## 共通の設計・検証

- 説明しすぎず、アイコン・数字・配置・図・実反応から推察させる。同じアイコンが複数あるだけで色・ID・正答・手順をラベルへ足さない。特徴的な位置だけ位置を添える。
- 実APIの観測を開箱条件にする。未対応・失敗・権限拒否・時間経過を、合意のない代替成功へ変換しない。
- ステージ追加・削除・統合では既存進捗を壊さない扱いを検討し、履歴の削除や新ステージへの無条件達成コピーをしない。
- 実装後はリポジトリの検証ルールに従う。コードはpnpm run check、振る舞いはpnpm run test:ci、配布影響はpnpm run build。索引変更は生成・差分確認も行う。
- 最終のPoC更新時は149テストとビルド成功。checkは完了したが、未変更の表にmarkuplintの警告、ビルドには既存の大きいchunk警告が出た。次のセッションで現在の結果を確認する。

## 次セッション用の初回プロンプト

以下をそのまま開始メッセージに使える。

```text
ステージレビューと事前PoCは終了したので、合意したステージの改修・削除・統合・分離・追加を実装してください。

まずAGENTS.mdと対象ルール、docs/notes/stage-review-implementation-handoff.mdを読み、そこから合意文書とPoC結果を確認してください。初回AIレビューの提案より、対話で確定した最新の方針を優先してください。

現ブランチと作業ツリーを確認し、既存のステージ済み・未ステージ・未追跡の変更を保全してください。PoCの完了とゲーム本体の実装完了を混同しないでください。

合意事項から実装作業表を作り、D→P→Lの順で、小さい作業単位ごとに実装・検証・記録を進めてください。最初の二ステージは現状維持なので、D-003/S-020から始めてください。依存する統合・分離はまとめて扱い、同じ方針の再確認のために止まらず、確定した範囲を進めてください。

以前確認済みのAPIの再PoCや、追加の人手確認を着手条件にしないでください。S-400はPCで確認した範囲で採用、S-700の新構成は受信機なしで保留です。未観測の環境差は実装時の確認事項として残してください。

各作業単位で必要な検証を行い、実装状態と人手確認状態を分けて作業表・レビュー記録を更新してください。既存の人手記録を自動で合格にしないでください。設計変更が必要な不成立や、最新の合意を判定できない矛盾だけを切り分け、他の確定作業は進めてください。
```
