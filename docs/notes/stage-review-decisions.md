# ステージレビューの方針

対話で合意した、今後の P・L レビューにも適用する方針。個別の現行仕様は各ステージのコード、確認範囲と進行は[レビューの進行](./stage-review.md)、未決事項は[残作業](./remaining-work.md)を参照する。

## パズルの作り方

- タイトルは題材や雰囲気を示唆し、具体的な解法や操作の説明にしない。
- 操作できるもの、現在の状態、目指す関係は、図・配置・動き・音・数字や API の実際の変化から推測できるようにする。説明を消すだけで、根拠のない当て物にしない。
- API の機能を順に試すだけの構成は見直す。タイミングや実機操作を使う問題も採用できるが、単に待つ時間・外部機器や環境の所有を推理の難しさと混同しない。
- 解法そのものは原則として文章で先に教えない。一方で権限の用途、取得・保存、外部サービス、費用、設定変更の影響、拒否、未対応、エラー、解除などの必要な説明は隠さない。
- 視覚・音の手掛かりは読み上げ等でも得られるようにし、支援技術向けの文言だけで正解を明かさない。箱の読み上げ名は基本的にアイコン名とし、同じアイコンが複数あるだけで色・ID・解法を付け足さない。
- 同じ API を使うことや似た題材だけで統合・削除を決めず、プレイヤーの体験を比較して個別に判断する。

## 実装・検証

- 本物の API の値やイベントで達成を判定し、未対応・拒否・失敗・推測値を成功にしない。固定の合言葉は、その入力自体を別箱の達成や隠しフラグで制限しない。
- ステージ ID と箱 ID は進捗に使う。統合・分離や条件変更では既存履歴を保全し、異なる条件の達成として自動転記しない。
- 事前 PoC、製品実装、自動テスト、人手での内容レビュー、実機・ブラウザ別確認を混同しない。未観測を合格へ変換せず、以前成立を確認した API の再 PoC や追加の人手確認を他の確定作業の着手条件にしない。
- 個別レビューの履歴やチェックリストを重複して残さず、決定した内容はコードへ反映する。確認範囲はユーザーの最新報告を優先し、古い「未確認」を再び残作業として扱わない。
- S-400 の事前 PoC は PC で確認した範囲で採用済み。S-700 の新構成は受信機なしで保留し、現行構成を維持する。
- S-630 は実際に使用する接続種別 API の対応環境が限定されるため L に分類する。ステージと箱の ID は維持する。

## 将来の候補

- 照度の暗・明の収集は、実センサーが通常環境で利用可能になった際に到達性や既存の体験との重複を再検討する。現行ステージへの復帰は未決定。
- 通信量低減の設定を使う問題は、対応ブラウザが利用可能になった際に再検討する。未対応を成功にしない。
- その他の未採用案は[新規ステージ・ギミック案](./stage-gimmick-ideas.md)を参照する。
